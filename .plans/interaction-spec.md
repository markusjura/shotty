# Shotty interaction specification

Revised 25 September 2026 after Markus's review of the first preview. This document defines the intended native behavior. It takes precedence over the first preview and over older conflicting UX details in the implementation plan.

## UI refinement confirmed on 26 September 2026

Markus supplied native CleanShot reference images and asked for matching thumbnail and scrolling chrome within Shotty's existing feature scope. These instructions supersede the earlier permanent thumbnail action-row requirement: previews fill rounded, subtly bordered cards edge to edge; Close, Edit, Copy, and Save appear in a hover or keyboard-focus overlay. Pin and cloud actions remain outside scope. Copy success transitions to a checkmark inside Copy and stays for that card; it must not add a success strip over the image. Medium cards are 220 × 160 points. Newest is nearest the bottom-left anchor by default; removing a card closes the gap with a brief slide, respecting Reduce Motion. Existing placement choices, successful-drop dismissal, Option-to-keep, and failure retention remain. Markus later removed dismissal Undo: Dismiss is final, as in CleanShot, and Dismiss All confirms when captures are unsaved.

Follow-up on 26 September: hover controls match CleanShot's proportions. Cards use a 13-point corner radius, 22-point corner buttons with heavy glyphs in one 8.5-point optical box (xmark and a drawn solid pencil), and 52 × 27-point Copy and Save pills in 12-point semibold. The hover background is the capture itself, blurred about 7 points and darkened, built once per card on first reveal. Shotty's floating chrome shares one small set of tokens in `Shotty/Design/Chrome.swift`: light control fill, dark control label, scrim, readout fill, hairline, radii, pill height, control font, and fade/move durations. Overlay buttons and "N more" use the same capsule style. Windows, forms, the editor, and popovers keep system colors, materials, and controls. Settings uses a native split view like Finder: a full-height translucent sidebar under the traffic lights, a toolbar that blends into the pane, and a centered 15-point semibold title.

Scrolling selection uses an instruction pill, white corner/edge handles, and Start Capture below the selection. Active capture uses compact Auto Scroll/Pause/Resume, Cancel, and Done capsules and an adjacent stitched preview. Keyboard, physical takeover, recovery, and export behavior remain unchanged. Settings should be narrower with a centered title in a standard compact titlebar, concise helper text, and no clipped controls.

Second follow-up on 26 September, from side-by-side comparisons. These points supersede conflicting details below.

- Thumbnail hover puts Edit in the top-right corner, opposite Close.
- The editor toolbar has Crop as its own group left of the drawing tools. Redact uses a pixel-grid symbol and Spotlight (never "Dim") a highlighted center in a frame. Tool options follow CleanShot: a Color button showing the current color with a chevron opens a swatch palette plus a custom well; Thickness opens a checked list of preset widths drawn at their weight; Arrow style, redaction style, and spotlight shape open checked lists with rendered samples. There is no separate Options popover or reset action. Copy and Save are icon-only buttons left of the text Done button. The bottom bar holds only zoom (left) and the drag handle (center); the Objects list is removed.
- Tool styles are not settings. Every option change applies to the selection and becomes the default for new objects, so the editor reopens with the last configuration.
- Capture settings drop Reveal in Finder, the file-name template (the default name is always used), Adjust before capturing, crosshair, magnifier, and Include pointer. The pointer-display fullscreen choice is called "Current display".
- Shortcut settings have two sections, Capture and Editor (tools included). Thumbnail commands have no shortcut settings and the CleanShot preset is removed.
- The pointer readout appears only while no region exists or while dragging, and never in scrolling capture. Scrolling has no axis choice: the first accepted movement decides it, and Auto Scroll goes down until then. After selection only Start Capture is shown; Escape discards the region. Once capturing, Cancel and Done sit below the region and Auto Scroll sits inside it at the bottom edge until the user scrolls by hand. There is no preview or status panel beside the region; a notice appears next to Cancel only when something needs attention.

## Product standard

Keep only the capture, annotation, output, and settings features Markus needs, then finish those features to a high standard. Small scope does not mean crude tools, unfinished input handling, generic icons, or missing configuration. Do not expand scope to compensate for weak execution.

The first preview did not meet this standard. Its title row plus wrapping tool row wasted space, fixed-size click placement misrepresented drawing, a black rectangle misrepresented the requested redaction treatment, and simulated controls were not distinguished clearly enough from working interactions. These were preview shortcomings, not acceptable implementation shortcuts. The solid-only redaction decision in the first plan was also wrong and is replaced below.

## Window composition and icons

The editor has one integrated title/toolbar row, approximately 48–52 points high. Native traffic lights sit on the left, followed by a stable tool group, a divider, the active tool's compact controls, flexible space, and Save/Done actions. No document-title strip above the tools and no permanent inspector row below them. The image starts directly under this row. Filename and dimensions belong in the window's accessibility title, document menu, or a quiet bottom status area.

The bottom bar is approximately 32–36 points high: zoom control at left, drag-export affordance in the center when useful, and Copy Image at right. Undo/redo live in Edit and have their standard shortcuts; they need not consume top-row width. Color, width, arrow style, text style, redaction style, and spotlight shape use compact popovers with visual samples. The selected tool stays in a fixed position as its options change.

At normal desktop width all ten requested tools fit. As width decreases, collapse style controls to one labeled Options popover before moving tools into an overflow menu. Keep Select, the active tool, Save/Done, and Copy reachable. Never wrap tools into a second line or make the entire toolbar horizontally scroll. Set a practical native minimum width after testing the translated labels, initially 720 points. The web preview may show a compact overflow presentation below that width, but that is not a proposed phone UI for the app.

Use SF Symbols at a consistent optical size and weight for native standard actions. Verify the actual symbols in the selected SDK rather than guessing names. Selection is a pointer; arrow is an arrow; rectangle and ellipse are outlines; line is a line; text is a typographic A; crop uses the familiar crop corners. Redact should read as pixelated cells, Spotlight as an opening in a dimmed frame, and Counter as a number in a circle. A hash symbol and a flashlight are poor semantic substitutes. Where SF Symbols has no suitable mark, draw one small original vector asset with matching stroke weight and optical bounds. Do not mix icon families or copy CleanShot assets.

Controls need optical alignment, clear selected/hover/disabled states, standard focus rings, tooltips containing the active shortcut, and comfortable hit areas even when the glyph is small. Use neutral chrome and one restrained selection accent. Annotation colors are content and can include useful red, orange, blue, white, and black presets. Light/Dark changes chrome only. Respect system contrast, transparency, and motion preferences.

## Shared editor gesture model

Drawing is direct manipulation. Pointer-down establishes the anchor, movement updates a live preview, and pointer-up commits one object and one undo transaction. Rectangles, ellipses, lines, arrows, redaction, spotlight, and crop use this model. A click with no meaningful movement creates no accidental tiny object. Draw in any direction. Clip acquisition at the source bounds; support edge auto-pan when zoomed, without generating annotations outside the source unless that feature is explicitly added later.

Keep the chosen drawing tool active after completion, matching the observed CleanShot rectangle behavior. The completed object can show handles for immediate correction; dragging its handle edits it, while drawing on empty image content creates the next object. V selects/moves objects. Escape cancels an in-progress gesture, then deselects on the next use; it does not unexpectedly close the editor. Space temporarily pans while held and returns to the previous tool on release.

Shape outline hit targets should be more generous than their visible strokes, with an initial 6-point tolerance. Handles stay approximately 7–8 points on screen with at least 12-point hit areas regardless of zoom. Pick the nearest visible edge of the topmost object; a hollow rectangle's entire interior must not block selecting objects beneath it. Shift-click toggles multi-selection. Marquee selection, delete, duplicate, Option-drag duplicate, and axis-locked movement are part of finished selection behavior. Do not add an always-visible layers sidebar.

Shift locks rectangle/ellipse proportions or line/arrow angles to 45-degree increments. Arrow keys nudge selected objects one image pixel; Shift nudges ten. Option while drawing from an anchor expands a shape from its center. Context menus offer relevant operations, including duplicate, arrange, delete, and edit text. These are Shotty decisions informed by native conventions and documented CleanShot modifiers, not claims that every combination was tested in CleanShot.

Store pointer positions in image coordinates through one invertible viewport transform. Visual handle sizes and hit tolerances use screen coordinates. Preserve the point under the pointer when zooming. Do not change geometry or stroke width when zoom changes. A cancelled gesture restores its pre-gesture state without adding an undo step. Text editing, slider drags, and object transforms each group into meaningful undo operations.

### Redaction appearance and correctness

Pixelation must be an image treatment with a well-chosen block scale, not a checkerboard painted over the image. Sample the source region, compute a stable block grid anchored to image coordinates, and render a crisp mosaic. Prevent the grid from shimmering as a handle moves; resizing reveals additional blocks rather than rearranging existing ones. Strength maps to image-pixel block size and must be consistent between Retina, zoom levels, preview, copy, drag, and save. Assess content-independent perturbation/randomization as an implementation detail rather than claiming it guarantees secrecy.

Blur uses a smooth filtered result with a sensible strength range, padded source sampling, and clipping to the requested region. Avoid dark seams from missing edge samples and repeated blur accumulation. Recompute from the immutable source/composited content at the redaction's z-position, never from the already blurred preview. Cache affected tiles and invalidate only changed regions. Overlapping redactions need a deterministic compositing order, and moving/resizing one must not reveal stale cached pixels. The preview may use a browser blur implementation; the native app uses Core Image and is assessed independently.

Solid is opaque covering, with neutral dark/light presets and optional matching color. It remains available but is not the default or the only implementation of Redact. Pixelate and Blur obscure visually; Solid completely replaces the selected pixels. This distinction belongs in concise tool help. Do not use the name “Secure Blur” or claim equivalence to CleanShot's security treatment without validating our own algorithm; CleanShot's label is observed behavior, not a public algorithm specification.

All exports flatten the chosen effect into pixels and omit editable layers, original rasters, OCR strings, and embedded source previews. Flattening does not make blurred/pixelated content mathematically unrecoverable. The editor must also represent prior output honestly: a redaction does not recall a raw image that was automatically copied, saved, or shared before editing.

## Copy, save, done, zoom, and drag

CleanShot's observed Copy Image shortcut is `⇧⌘C`. Its Save as tooltip says “Choose export location and exit (⌘S)”; official documentation also describes Option variants that keep the editor open or skip the save dialog. Shotty retains familiar shortcuts but makes the behavior explicit:

- Copy Image copies the flattened current result with one click. `⌘C` retains selected text/object meaning. Default Copy keeps the editor open, with Close after Copy in Settings; Option-click temporarily inverts the close preference.
- Save writes to the configured folder with one click. `⌘S` does the same; `⇧⌘S` or Option-Save opens Save As. Default Save keeps the editor open, with Close after Save configurable. Surface the selected destination in help/context menu; do not force a save dialog on every capture.
- Done (`⌘Return` outside text/crop editing) commits the editable result back to its thumbnail and closes the editor. It does not silently copy, write a file, or delete the capture. Thumbnail reopening restores the annotations. If the thumbnail was dismissed while editing, Done recreates it. Closing an editor without a retained thumbnail and with unexported work offers Save / Keep as thumbnail / Discard / Cancel. Avoid repeated save prompts when the thumbnail already safely retains the session.
- Zoom sits bottom-left: fit, 100%, presets, plus `⌘+`, `⌘−`, `⌘0` Fit, `⌘1` Actual pixels, pinch and Space-pan. At 100%, one image pixel maps to one display backing pixel; the label must be consistent on Retina displays. Keep 1× logical export scaling a separate option, not an ambiguous zoom command.
- Drag the image from a dedicated bottom handle or thumbnail using a native file promise, without switching tools. Create the flattened export only when needed; cancel leaves the session intact. No extra confirmation for the ordinary drag action.

## Thumbnails and settings

CleanShot documents quick copy/save/drag, swipe dismissal, context actions, configurable location/size/auto-close, and multiple-overlay commands. Its exact live hover/stack behavior was not fully verified. Markus's required behavior is authoritative: each capture gets a persistent thumbnail, clicking opens the editor, and inner controls save or close that item.

Follow active display is the default and applies to the entire existing stack as the pointer moves between displays. No click is required. Do not wait for the next capture. Keep capture identities, order, edits, save state, and remaining timeout intact. A new capture joins the stack at its current destination, regardless of which display supplied the pixels. Settings also allow Main display or a named connected display.

Markus confirmed that pointer movement alone relocates CleanShot's stack. Target the current pointer display without requiring a click; keep the last valid target only when the pointer cannot resolve to a connected display. Filter boundary jitter. Freeze relocation for a card press, drag, menu, or keyboard operation, then resolve the pointer display after it ends. Moving the stack never activates Shotty or raises an unrelated editor. Preserve its edge anchor within the new screen's visible frame and backing scale. Handle Spaces/fullscreen and unplug/replug without losing captures; a disconnected fixed display temporarily falls back to main and restores its preference on reconnection. CleanShot's exact latency is unmeasured; the interaction locks are Shotty decisions.

Use image-first cards with clear close and save hit targets that never activate the editor accidentally. Preserve older cards, show the newest with a brief restrained entry treatment, and keep the stack anchored to the selected screen edge. Show Copy alongside Save in the focused/expanded card; all actions remain keyboard-accessible and available in a context menu. Do not require hovering to discover the two requested save/close actions. Avoid permanent per-card metadata bars unless needed for failure/progress. Batch overflow goes into a reachable stack drawer, never silently discards captures.

A successful card Save can dismiss it according to settings. Failure leaves the card and offers Retry/Choose folder. Dismiss does not remove exported files. Dismissal is final; there is no Undo. Drag and swipe are native gestures with motion/threshold behavior tested on trackpad and mouse. Never install global key monitors merely to make hover shortcuts work: focus the card intentionally before local keyboard commands apply.

The right-click menu is limited to Open Editor, Copy Image, Save to Folder, Save As…, and Dismiss. Show assigned shortcuts, use shared command handlers and availability rules, and apply commands only to the clicked capture. Escape closes the menu without dismissing the card. It must stay on its display until the menu closes. Pin, upload, share, rotate, flip, Open With, mail, and Quick Look are outside the requested feature set. Do not import CleanShot's full menu; ask Markus before adding an uncertain capability.

Settings retain six compact categories: General, Capture, Thumbnails, Editor, Shortcuts, Permissions. Appearance is System by default. Menu bar on, Dock off. Output choices are independent toggles; Downloads is the initial folder. Shortcuts use a recorder with clear conflict feedback and a small “Use CleanShot keys” migration preset. Permission status names what the permission enables and offers the appropriate System Settings link. Avoid a switch for basic expected behavior such as whether clicking a thumbnail opens its editor. Avoid performance knobs, separate style pages, or options that exist only because a prototype is incomplete.

### Native visual language

Use a flat macOS Settings window: one system window surface, a standard sidebar, and a form in the detail area. Group related controls with section headings, whitespace, and occasional system separators. Do not wrap the form, sections, rows, and controls in successive rounded boxes. Shadows belong to actual floating windows or popovers, not settings sections. This applies across the app, including editor chrome and capture controls.

Implement Settings with a SwiftUI `Settings` scene and a `NavigationSplitView` containing `List(selection:)` with sidebar styling. Use `Form` with the macOS columns style, `Section`, `LabeledContent`, `Toggle`, `Picker`, `Slider`, `Stepper`, and `ColorPicker` where appropriate. Prefer checkbox toggles for ordinary macOS preferences, radio/segmented pickers for a few mutually exclusive options, and menu pickers for longer lists. Keep system control sizing, focus rings, keyboard behavior, labels, enabled states, and accessibility semantics. Custom controls are limited to interactions with a real need, such as the shortcut recorder and screen-position preview; they must meet the same keyboard/accessibility requirements.

Use semantic primary/secondary text and system window, control, separator, and selection colors. Keep the neutral background palette with standard macOS blue as the app accent, as Markus requested. Configure the native app accent to system blue and use system tint/selection behavior for checkboxes, switches, focused controls, and primary actions; do not paint black switches or implement replacement control skins. System blue must adapt to Light/Dark and accessibility contrast. Use SF Symbols with consistent optical size and native weights. Materials are supplied by the system for sidebar/titlebar/floating chrome where appropriate; do not add glass effects or blur behind every group.

Settings use the native titlebar, traffic lights, responder chain, standard `⌘,` command, and system folder/color dialogs. Changes apply immediately; validate consequential settings inline. Persist preferences in the existing typed store without duplicating control state. System appearance follows macOS; explicit Light/Dark also updates AppKit-owned panels. Verify Full Keyboard Access, VoiceOver labels and order, Increase Contrast, Reduce Transparency, Reduce Motion, disabled controls, and long labels in the actual native window.

The web preview is for hierarchy, density, and interaction alignment. Browser-native checkboxes/radios/selects still differ from SwiftUI/AppKit rendering; its colors, titlebar, material, focus rings, and font metrics are approximations. Native implementation must use the standard components above rather than translate the CSS. The previous box nesting was a design choice and has been removed; it was not an unavoidable web limitation.

## Native implementation quality gates

Use AppKit pointer and responder-chain handling around the SwiftUI shell. One canvas/document transform, one command registry, one export renderer. `NSUndoManager` groups complete gestures. Native text input handles marked text and IME composition. Pointer-up outside the view and cancellation on focus loss must resolve correctly, with no stuck drag. Do not rebuild the SwiftUI view tree or encode the source on every pointer event.

Rendering must distinguish source, effect tiles, vector annotation layers, transient interaction preview, and selection handles. The last two never export. Reuse a `CIContext`; process dirty effect tiles off-main with generation IDs so slow earlier renders cannot overwrite a newer strength setting. Preview effects can progressively refine during a gesture, but completed exports always use the full-resolution canonical render. Test color-profile consistency and exact edge coverage at 1×/2× and non-integer zoom.

For each included tool, completion requires create → adjust → restyle → undo → redo → copy/save → reopen, at both fit and magnified zoom. Exercise reverse drags, modifier changes during a drag, sub-threshold clicks, release outside canvas, cancellation, overlapping annotations, text-focus conflicts, keyboard-only edits, and accessibility labels. Review icon optical balance and hover/selection states at native scale in both appearances. Measure pointer latency and frame cadence on both fleet Macs rather than treating a web preview as performance evidence.

For capture modes, completion requires the fast normal path plus cancellation, denied/revoked permission, multi-display changes, and configured output combinations. Scrolling also requires no unsolicited automation after selection/Start, Auto Scroll disappearing on the first manual scroll, no keyboard/menu bypass of manual-only mode, preserved accepted content, and eligibility resetting only for a new capture. Test Auto Scroll → pause/resume and the proposed Auto Scroll → manual-only handoff separately. Test physical versus injected input, horizontal content, sticky headers, nested scrolling, changing content, and visible recovery from an unreliable seam.

Thumbnail acceptance includes two existing edited captures relocating between different-scale displays without another capture, pointer-only and click transitions, no focus theft, no movement under an active press/drag/menu, overflow on a smaller display, Spaces/fullscreen, disconnect/reconnect, and Accessibility denied. Moving a thumbnail stack must never change captured pixels or re-encode its documents.

## What the interactive preview can establish

The preview is an interaction study, not the native app. The revised editor should demonstrate genuine drag-defined geometry, live preview, selection/move/resize, text entry, counters, undo/redo, zoom-aware input, and visible pixelate/blur effects. Those interactions let Markus assess ergonomics; the preview cannot establish AppKit feel, ScreenCaptureKit timing, native text fidelity, OS permissions, cross-app file promises, reliable OCR, stitching, privacy guarantees, or export correctness.

The preview must expose a concise “Prototype limits” note outside the depicted app. Any incomplete action must say it is simulated or unsupported. Do not display a successful real save/copy message when no file or clipboard write occurred. If crop, pan, curve editing, keyboard gestures, or another listed behavior is omitted in the preview, list the exact omission. The native interaction specification remains the implementation requirement.
